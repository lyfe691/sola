# A multi-provider AI chat that runs on your own API keys

[Luma](https://luma.ysz.life) is a chat app for people who already pay for API access with one or more model providers. You add your keys once, pick a model for each chat, and every request goes to that provider on your key.

## Picking a model

The model button in the input opens a picker with every model Luma offers, grouped by provider. A rail of provider logos jumps between the groups, the search box filters as you type, and small icons mark what each model handles, such as reasoning, images as input, tool use and PDFs. A star adds a model to a favourites list on the rail.

Each chat keeps its own model, so one conversation can run on Claude and the next on GPT-5 Mini. Models whose provider has no key yet carry a lock, and picking one puts a note above the input that names the missing key, with a button that opens settings.

## Asking

The input takes text, images and files such as PDFs, CSVs and Markdown, pasted, dropped onto it or picked from the plus menu. The same menu sets a mode for the next message. Create image asks the model to answer with a picture, Web search has it look things up and cite its sources, and Study and learn asks for structured teaching with worked examples.

## Answers

Replies stream in as Markdown. Code blocks are highlighted and carry copy and download buttons, and maths and diagrams render in place. When a model reasons before it answers, the reasoning folds into a "Thought for N seconds" row above the reply, and Claude models get extended thinking without anything to switch on. Answers from a web search carry their sources as small chips next to the sentences that use them.

## Editing, retrying and finding chats

Nothing in a conversation is overwritten. Editing a message you sent adds a new version next to the old one, with a fresh reply under it, and arrows under the message flip between the versions. Retrying an answer does the same on the reply side, and the retry menu can send the question to another model, so two models' answers to the same message sit one arrow apart.

New chats are titled by a small, cheap model on one of your keys. The sidebar lists them with the pinned ones first, and each can be pinned, renamed or deleted from there. Ctrl+K searches every chat, grouped by date, and the other common actions have shortcuts too: a new chat, the file picker, the model picker, the sidebar. Settings can export all your chats as a download, or delete them.

## Your API keys

Settings has a row for every provider, each with a link to the page where you get a key. Luma tries a new key against the provider before it saves it, so a key the provider rejects is refused on the spot. Keys are encrypted before they're stored, and the browser only ever learns which providers have one.

## How it's built

Luma is a Next.js 16 app on React 19. The Vercel AI SDK streams the replies and reaches each provider through that provider's own package, Supabase holds the accounts, the chats and the uploaded files, and the streaks on the start screen are a Three.js shader.

### Conversations are trees

Every message is a row with a `parent_id`, and a chat stores one more pointer, `active_leaf_id`, to the last message of the thread on screen. The thread is derived: start at the active leaf, follow parent pointers up to the root, reverse. An edit or a retry adds a sibling under the same parent, and the walk marks each message that has siblings of its own role with its place among them, which is all the arrows under a message read.

<CodeBlock
  code={`export function buildTimelineMessages(
    graph: ChatGraph,
    activeLeafId: string
  ): UIMessage[] {
    const path = getPathToLeaf(graph, activeLeafId)
    if (path.length === 0) return []
    return path.map((node) => {
      const siblings = (graph.childrenByParentId.get(node.parentId) ?? []).filter(
        (candidate) => candidate.role === node.role
      )
      const branchCount = siblings.length
      const branchIndex = Math.max(
        0,
        siblings.findIndex((candidate) => candidate.id === node.id)
      )
      return {
        id: node.id,
        role: node.role,
        parts: node.parts,
        metadata: {
          createdAt: node.createdAt,
          ...(branchCount > 1
            ? ({
                branchCount,
                branchIndex,
                isActiveBranch: true,
              } satisfies ChatBranchMetadata)
            : {}),
        },
      } satisfies UIMessage
    })
  }`}

Switching versions is a server call that takes the next sibling, follows the newest child down to a leaf and saves that leaf as the active one. The cost of the design is that opening a chat reads every message in it, including the branches you aren't looking at. In exchange they arrive in one query on an index over chat and creation time, and the tree code is plain TypeScript that the browser and the server both import.

### From a model id to a provider client

Model ids carry their provider, as in `anthropic:claude-opus-4-6`. The chat route checks the id against the catalogue and falls back to the default when it isn't there, so the browser can't ask for a model Luma doesn't list. The prefix selects the user's key, which is decrypted for that one request, and the provider's AI SDK package, which is loaded with a dynamic `import()` so a request only pulls in the SDK it needs. Providers with an OpenAI-compatible API reuse the OpenAI package with their own base URL, so adding one is a catalogue entry.

### Keys at rest

A key is encrypted with AES-256-GCM under a fresh random IV and stored as IV, ciphertext and authentication tag. Because GCM authenticates the ciphertext, a value changed in the database fails to decrypt instead of turning into a different key. This protects the keys in a leaked database dump. The server has to call providers with the plaintext key, so it can decrypt every key it stores, and so can anyone who holds both the database and the master key.

### What goes back to the model

A stored reply keeps everything the screen shows: reasoning, text, tool calls and their results. The history sent with the next request is rebuilt from the tree on the server, and three things are stripped from it first. A generated image is swapped for the text `[image was generated]`, because the base64 would otherwise ride along with every later request. Reasoning stays on screen but is never replayed, since OpenAI's Responses API can reject reasoning items from history. Provider metadata is deleted, which also keeps a thread usable when the next turn goes to a different provider.

Attachments stay in a private bucket, and each request signs fresh links to them that expire after ten minutes.
