# A consulting site its owners publish themselves

perspectas gmbh is a consulting and recruiting firm in Wetzikon ZH: two partners, working for small and mid-sized Swiss companies. Their previous site was a WordPress install. Dominik Künitzer and I scoped the project with the client; the design, the build, the hosting setup and the handover are mine.

## The constraint that picked the stack

The ask was not a new coat of paint. The partners had a new positioning to express (consulting and recruiting, advisors rather than placement agents), a smaller site to fit it into, and one hard requirement: they wanted to change their own text without asking anyone. The old stack never gave them that.

So every word a visitor reads lives in Sanity. Seven document types, five object types, and one settings singleton holding every fixed line on every page along with the Impressum and the Datenschutz. Services, projects, testimonials, the people on Über uns, the contact details: all editable, and publishing is a click.

## One loud colour, one curve

The corporate manual gives five colours. The site spends four of them quietly and one loudly: the yellow of the logo dot, on an off-white ground with the corporate grey as the text colour. No component hard-codes a hex value; the five are custom properties exposed as Tailwind utilities. The headline's full stop is that dot, springing into place once the last word of the h1 has landed.

It renders inside the last word's box, so it can never wrap onto a line of its own. Type is Roboto, self-hosted as one variable file per style rather than fetched from Google at runtime, because the site runs on the client's own server and I did not want a third party in the first paint. Motion uses one curve and one viewport trigger, 0.6 to 1.1 seconds, and nothing loops.

The Leistungen accordion came from the client verbatim: «Titel sicher sichtbar, Detailtext vielleicht zum aufklappen.» The first item opens by default, so the fold is never a secret.

## Getting a publish onto the page

Every Sanity query names the document types it reads, a webhook revalidates by type, and an hourly floor sits under all of it.

<CodeBlock
  code={`export const client = createClient({
  projectId,
  dataset,
  apiVersion,
  useCdn: false,
  perspective: "published",
  stega: false,
})
// The webhook revalidates by _type, so this list is the single source
// for both sanityFetch and /api/revalidate.
export const CACHE_TAGS = [
  "siteSettings", "service", "project", "testimonial",
  "clientReference", "teamMember", "partner",
] as const
client.fetch<T>(query, params, {
  cache: "force-cache",
  next: { tags, revalidate: 3600 },
})`}
  fileName="lib/sanity/client.ts"
  lang="ts"
/>

Reads go to the Sanity API rather than its CDN (`useCdn: false`): a re-render triggered by the webhook would otherwise pick up the CDN's older copy and cache it for another hour. Visitors are served from Next's cache either way, and only a regeneration pays for the uncached read. The hourly floor is the backstop. If the webhook breaks, the site is an hour behind rather than frozen at the last build.

Once the partners were editing content themselves, changes from my side stopped going through the seed script, which replaces whole documents. They go in as field patches instead: printed as a dry run first, each pinned to the revision it was written against, applied in one transaction.

## Two integrations that needed care

The client's job board ships as a web component that injects its own CSS, jQuery and fonts, so it runs in a sandboxed iframe that reports its own height by `postMessage` and has the page's colour tokens handed in. It reads as part of the page in both schemes and cannot touch the layout around it.

The other rule is about motion: rendered markup never branches on `useReducedMotion()`, because it returns false during SSR and true on a reduced-motion visitor's first client render. One tree, with only the values switched after mount, keeps hydration clean.

## What handover means here

The hosting account is in perspectas' name, with me as an invited user, so their access outlives mine. Redirects catch the URLs of the old site that search engines had indexed.

None of that is visible on the site. It is the part that decides whether a client stays stuck with their developer, and it has to be arranged before the handover rather than renegotiated after it.
