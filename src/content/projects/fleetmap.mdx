# A delivery fleet, live on an office TV

fleetmap tracks a delivery fleet in real time. Each van's phone posts its GPS position to an API; a screen in the office moves that van's marker, draws its route, and shows how far behind schedule it is. Orders are never typed in. Below: the two data flows the whole system reduces to, and why the order sync is a diff instead of a rewrite.

## What the console shows

Three views share one layout:

- **Live Map**: every van as a marker, colored by whether it is on route, waiting, behind schedule or stale.
- **Live Tracking**: one van in detail, with distance driven today, current speed, stops left, and the day's itinerary as a numbered timeline of planned pickups and dropoffs.
- **History**: a chosen day replayed from the recorded GPS track, scrubbable and playable at 10x to 120x.

The interface runs in English and Swiss German, in a light or a dark theme.

## Two data flows, one thin API

GPS is a push. The phone posts to `POST /api/location`, authenticated as that driver and scoped by row-level security so a van can only be written by its own driver. The handler puts the latest position on the vehicle row and appends to history; Supabase Realtime broadcasts the row change and the dashboard moves the marker. There is no Redis and no WebSocket server of mine. Fan-out is the database's job, which took an entire service out of the deployment.

Orders are a pull. A worker polls the fleet API of the route optimizer the operation already runs, every 60 seconds, and mirrors each rider's routes into `orders` and `stops`. Route lines and ETAs come from `GET /api/route`, a thin proxy in front of OSRM (an open-source routing engine) which I self-host on a Switzerland extract, rather than pay a hosted routing API per request for a screen that recomputes all day.

## Why the order sync is a diff, not a rewrite

The obvious 60-second poll deletes the vehicle's stops and re-inserts them. It works, and it is unusable: every tick emits a Realtime event for every row, the dashboard's route cache (keyed on stop id, sequence and status) misses on all of them, and the map redraws a route that did not change. It is re-printing the whole delivery sheet every minute because one box got ticked.

So the mirror is a single Postgres function that diff-applies the picture for one vehicle. Matched stops are updated only where a column actually differs:

<CodeBlock
  code={`update stops set
  seq    = (s->>'seq')::int,
  status = s->>'status',
  eta_at = nullif(s->>'eta_at', '')::timestamptz
where id = v_stop_id
  and (
    seq    is distinct from (s->>'seq')::int or
    status is distinct from s->>'status' or
    eta_at is distinct from nullif(s->>'eta_at', '')::timestamptz
  );`}
  lang="sql"
/>

Abridged: the real guard covers seven columns. Unchanged rows are never written, so they emit nothing, and stop ids survive across ticks. Stops that vanished from the optimizer's picture are deleted, which makes an empty payload a valid instruction: clear this vehicle.

## Made for a screen that stays on

Production is Docker Compose on a single server: the Next.js app, the sync worker and OSRM beside a self-hosted Supabase stack. Nothing reads as late until it is five minutes late, so a minute of traffic doesn't flap the map red.

The TV never sees a password. It presents a display code and gets a read-only session.

The rule that decided most of this build: push the work into something that already exists — the database, the optimizer, the routing engine — and keep the API thin enough that there is nothing in the middle to debug.
