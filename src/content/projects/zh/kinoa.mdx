## 找到想看的

首页只有一行标题和一个搜索栏，一个白色小家伙从搜索栏边缘探出头来。结果在你输入时就陆续出现，第一个以你输入内容开头的标题，其余部分会以灰色自动补全。小家伙会跟着光标走，没有匹配结果时一脸困惑，输入框被清空时则眼泪汪汪。

## 一起观看

房间就是一个链接。房主选好作品并分享房间，所有加入的人看到的是同一个时刻，播放器旁边有聊天窗口。房主暂停、跳到后面或换集时，房间会跟着变，落后的来宾会看到一个 Catch up 按钮。房主同时还负责管理房间：

- **移交**：房主可以把房主身份交给房间里的任何人。房主离开时，房主身份会立刻交给下一个人；如果房主没有离开房间就关掉了标签页，仍在房间里的某个人会在大约两分钟后接手。
- **管理**：房主可以移除某人。创建房间的人在担任房主期间，还可以禁止其再次加入。
- **可见性**：公开房间会列在 Watch Together 页面上，私密房间则只能通过链接加入。

## 个人主页、动态与私信

播放器周围有一个小型社交网络：

- **个人主页**：认领一个用户名后，账号就有了一个位于 `kinoa.to/@name` 的页面，上面有封面图、简介，以及活动、收藏和片单几个标签页。一个开关就能把这些标签页设为私密，名字、简介和粉丝数仍然可见。

## 设计与动效

Kinoa 的默认外观是嵌在灰色边框里的白色页面，深色主题下则近乎全黑，蓝色只留给焦点和选中状态。除非你自己选定，它会跟随系统的浅色或深色设置；设置页里还有其他主题，也可以自己设定颜色和对比度。侧边栏里，当前页面画成一个与内容面板连在一起的标签，选另一行时，这个标签会流到那一行。其余的动效都很细微，用来确认刚刚发生了什么：

- 菜单和弹出框从打开它们的元素中展开，菜单还会给背后的页面蒙上一层毛玻璃。
- 对话框平滑地改变大小，切换步骤时按钮保持在原位。
- 页面逐步流入，每个部分出现在它的占位符原来所在的位置。
- 被拒绝的表单会让出错的输入框抖动。

对于在系统里要求减少动态效果的访客，动效会退让。Kinoa 也可以作为应用安装：在电脑或 Android 上直接从浏览器安装，在 iPhone 上则跟着一份简短的指引操作。

## 实现方式

Kinoa 是一个 Next.js 应用，以服务端组件为主，账号、数据库以及房间所依托的实时频道都建在 Supabase 上。它部署在 Vercel 上，用 next-intl 做翻译。

### 让房间保持在同一个时钟上

嵌入式播放器是最硬的限制：没有办法让它们暂停或跳到某个时间点。所以，与房主进度拉开差距的来宾，会把自己的播放器重新加载到房主所在的位置，并按一次重新加载所需的时间向前推算。每次重新加载都会测出它实际落在哪里，并据此修正下一次，而且目标是落在房主之后零点几秒，因为提前会破坏一个场景，落后则不会。

<CodeBlock

  /** Share of each landing error folded into the next lead estimate. */
  export const LEAD_LEARNING_RATE = 0.6
  export function anchorTargetFor(
    host: HostAnchor,
    now: number,
    leadSeconds: number
  ): AnchorTarget {
    if (!host.isPlaying) {
      return { time: Math.max(0, host.currentTime), play: false }
    }
    return {
      time: Math.max(0, projectPlayhead(host, host.at, now) + leadSeconds),
      play: true,
    }
  }
  export function nextLoadLead(lead: number, driftAtSettle: number): number {
    const error = driftAtSettle - TARGET_DRIFT_SECONDS
    const next = lead - error * LEAD_LEARNING_RATE
    return Math.min(
      MAX_LOAD_LEAD_SECONDS,
      Math.max(MIN_LOAD_LEAD_SECONDS, Number.isFinite(next) ? next : lead)
    )
  }`}

每次重新加载都要重新缓冲，所以房间只在必要时才要求重新加载：

| 发生什么                 | 何时                                         |
| ------------------------ | -------------------------------------------- |
| 房主的播放器发送播放位置 | 每 5 秒一次，以及每次播放、暂停和跳转时      |
| 每位来宾测量自己的偏差   | 每秒一次                                     |
| 出现 Catch up 按钮       | 与房主相差超过 4 秒时                        |
| 来宾自动重新加载         | 连续两次检查都偏差这么大时，最多每 20 秒一次 |
| 停止自动重新加载         | 重新加载 3 次仍未跟上时                      |

房间只用 VidFast 播放，因为这个办法需要一个从指定位置开始播放、而不是从上次停下的地方接着播的播放器。

### 按播出日期匹配动漫分集

Kinoa 里的一切，从链接到观看记录和评论，都用 TMDB id 来识别一部作品。动漫播放器要的却是动漫数据库 AniList 的 id 加上集数，而且两个片库切分作品的方式不同。TMDB 把 Re:Zero 的全部 85 集列为一季，AniList 则为每个部分各建一个条目：

| AniList 条目     | 集数 | TMDB 第 1 季 | 播出    |
| ---------------- | ---- | ------------ | ------- |
| 第 1 季          | 25   | 1–25         | 2016    |
| 第 2 季          | 13   | 26–38        | 2020    |
| 第 2 季第 2 部分 | 12   | 39–50        | 2021    |
| 第 3 季          | 16   | 51–66        | 2024–25 |
| 第 4 季          | 19   | 67–85        | 2026    |

所以 Kinoa 先查出一个 TMDB id 背后的 AniList 条目，再查每个条目的播出日期，然后按日期配对分集，前后允许相差一天。

日期对不上的分集，只有在紧挨着一个已确认的配对、而且两个片库在那一处未配对的分集数量相同时，才会配对。否则它就保持未配对，在普通服务器上播放，因为配错了会播错集，而少一个配对只是换了服务器。在我检查过的 30 部热门作品中，这种方法能配对 99% 到 100% 的分集。

### 由数据库执行的规则

有三条规则放在数据库里，而不是应用里，因此对任何客户端都成立：

- **只有房主能操控房间**：这是加在房间控制频道上的行级安全策略。一个集成测试会以来宾身份登录，发送踢人和同步之类的房主命令，并检查房主一条也没有收到。
- **被移除的来宾会立刻被切断**：Supabase Realtime 在客户端加入私有频道时检查频道的策略，也没有能把单个用户移出频道的调用。所以每个房间的频道名都带着一个密钥，每次踢人或封禁都会更换：其他人用新密钥重新加入，被移除的客户端则留在一个不再有任何写入的频道上。
- **用户名只在一处认领**：一个数据库函数掌管所有规则，从长度和保留名称，到内容审核和两次更改之间 30 天的等待期，而当两个人同时认领同一个名字时，由唯一索引来裁决。

### 更少的往返

有三项开销的执行次数远远超过了必要：

| 工作                                      | 之前                                                  | 之后                               |
| ----------------------------------------- | ----------------------------------------------------- | ---------------------------------- |
| 检查谁已登录                              | 电影页面上对 Supabase Auth 调用 3 次，动态页面上 4 次 | 每次渲染 1 次，由所有辅助函数共用  |
| 绘制片单                                  | 片单上的每部作品各发一次 TMDB 请求                    | 每页一次查询：每一行都自带它的卡片 |
| 每个打开的标签页每 5 分钟做一次的版本检查 | 每次都调用一个无服务器函数                            | Vercel 的边缘缓存                  |

检查会话并不是本地解码：它要走网络，所以每次渲染只做一次才如此重要。

### 保持翻译完整

每一条字符串都以英语为准。CI 里有一项检查（`pnpm check:i18n`），会把其他每个语言文件的键与它对照，缺少或多出某个键时就会失败。
