# Eine lokale Sandbox für OpenID Connect

Vault ist ein Identitäts-Setup, das auf einem einzigen Rechner läuft: Keycloak als OpenID-Connect-Provider, ein FastAPI-Backend, das dessen Tokens prüft und Rollen kontrolliert, und ein Next.js-Frontend mit Anmeldeseite und Dashboards, die nach Rolle freigegeben sind. OpenID Connect (OIDC) ist die Identitätsschicht auf OAuth 2.0. Ich habe Vault im Mai 2025 gebaut, um einem Token zu folgen, vom Moment, in dem Keycloak es ausstellt, bis zu dem, in dem eine API es annimmt oder abweist.

## Die Anmeldung

Das Anmeldeformular bleibt in der App. Das Frontend schickt Benutzername und Passwort per POST an das `/login` des Backends, und das Backend tauscht sie in einer einzigen Anfrage am Token-Endpunkt von Keycloak ein, mit dem Resource-Owner-Password-Grant, den Terraform am Client aktiviert. Das Access-Token, das es zurückbekommt, legt das Backend in einem `HttpOnly`-Cookie ab, das mit dem Token abläuft, nach den fünf Minuten, die Keycloak standardmässig vorgibt. Eine abgelehnte Anmeldung zeigt die eigene Fehlermeldung von Keycloak.

Bei diesem Grant sieht die App das Passwort des Benutzers, weshalb eine App mit echten Benutzern den Browser stattdessen auf die eigene Anmeldeseite des Providers schickt. Für eine Sandbox mit einem einzigen Demo-Benutzer ging es genau darum, den ganzen Austausch an einer lesbaren Stelle zu haben.

## Ein Portal, aufgebaut aus den Rollen des Tokens

Nach der Anmeldung ruft das Frontend das `/me` des Backends auf. Das Cookie ist `HttpOnly`, das JavaScript der Seite kann das Token also nicht lesen: Das Backend prüft es und liefert dessen Claims zurück, und das Portal wird daraus aufgebaut, mit dem Benutzernamen, einem Badge für jede Realm-Rolle und einer Schaltfläche für jedes Dashboard, das die Rollen freischalten. Der Demo-Benutzer hat beide Rollen und landet im Admin-Dashboard. Entzieht man ihm `admin`, zeigt die nächste Anmeldung ein Badge und eine Schaltfläche, und ein Aufruf von `/admin` führt stattdessen zum User-Dashboard.

## Die API entscheidet

Die Schaltflächen spiegeln die Rollen nur. Jede geschützte Route der API hängt von `verify_token` ab, das das Token aus einem `Authorization: Bearer`-Header liest oder, wenn es keinen gibt, aus dem Cookie. Ein fehlendes, abgelaufenes oder gefälschtes Token wird mit einem 401 abgewiesen. Ein gültiges Token ohne die passende Rolle bekommt von einer zweiten Abhängigkeit, `require_roles`, ein 403; sie sucht die Rolle im Claim `realm_access.roles` des Tokens:

| Route    | Braucht                       | Ohne das |
| -------- | ----------------------------- | -------- |
| `/me`    | Ein beliebiges gültiges Token | 401      |
| `/user`  | Die Rolle `user`              | 403      |
| `/admin` | Die Rolle `admin`             | 403      |

## Keycloak, konfiguriert mit Terraform

Docker Compose betreibt Keycloak 26.2 im Entwicklungsmodus, mit einer PostgreSQL-16-Datenbank für seinen Zustand. In der Admin-Konsole von Keycloak lassen sich ein Realm, ein Client, zwei Rollen und ein Benutzer in wenigen Minuten zusammenklicken, aber sie hält nicht fest, wie es dazu kam. In Vault steht diese Konfiguration in `terraform/main.tf`:

- **Der Realm**, `vault-core`, in dem alles andere liegt.
- **Zwei Realm-Rollen**, `admin` und `user`.
- **Ein Demo-Benutzer**, `demo`, der beide hat.
- **Der Client**, `vault-app`, über den sich die App anmeldet.

Eine geänderte Einstellung zeigt sich in einem Diff, und `terraform apply` bringt den Realm zurück auf genau das, was die Datei beschreibt.

## So ist es gebaut

Das Backend ist FastAPI, mit python-jose für die Token-Prüfung und httpx für die Aufrufe an Keycloak. Das Frontend ist Next.js mit Komponenten von shadcn/ui. Beide laufen auf dem Host, neben den beiden Containern.

### Ein Token prüfen

`verify_token` fragt Keycloak nie nach einem Token. Es liest das Discovery-Dokument des Realms unter `/.well-known/openid-configuration`, folgt dessen `jwks_uri` zu den öffentlichen Schlüsseln des Realms und lässt `jwt.decode` von python-jose die Signatur, das Ablaufdatum und den Aussteller prüfen, der Zeichen für Zeichen `http://localhost:8080/realms/vault-core` entsprechen muss. Keycloak signiert Access-Tokens mit dem privaten RSA-Schlüssel des Realms (RS256), zum Prüfen genügt also die öffentliche Hälfte. Beide Dokumente werden bei jeder Anfrage geholt statt zwischengespeichert: zwei lokale Roundtrips, und ein in der Admin-Konsole rotierter Schlüssel gilt ab der nächsten Anfrage.

Das Bearer-Schema wird mit `auto_error=False` erzeugt, sodass eine Anfrage ohne den Header bis zur Cookie-Prüfung kommt, statt auf der Stelle abgewiesen zu werden. Die Rollen sind eine zweite Abhängigkeit, die darübergelegt ist:

<CodeBlock
  code={`def require_roles(roles: List[str]):
      async def role_checker(payload: dict = Depends(verify_token)):
          if not has_role(payload, roles):
              raise HTTPException(
                  status_code=403,
                  detail=f"Access denied. Required roles: {', '.join(roles)}"
              )
          return payload
      return role_checker`}
  fileName="app/backend/main.py"
  lang="python"
/>

### Die Rollen stehen fest, wenn das Token ausgestellt wird

Terraform verwaltet die ganze Rollenliste des Demo-Benutzers. `keycloak_user_roles` ist abschliessend, der Benutzer hat also genau die Rollen in `role_ids`, und `realm_access.roles` im Token nennt nichts anderes:

<CodeBlock
  code={`resource "keycloak_user_roles" "demo_user_roles" {
    realm_id = keycloak_realm.vault.id
    user_id  = keycloak_user.example_user.id
    role_ids = [
      keycloak_role.admin_role.id,
      keycloak_role.user_role.id,
    ]
  }`}
  fileName="terraform/main.tf"
  lang="hcl"
/>

Streicht man `admin` aus `role_ids` und wendet die Änderung an, trägt ein vor der Änderung ausgestelltes Token die Rolle noch, bis es abläuft, weil das Backend dem vertraut, was das signierte Token sagt, und Keycloak nie wieder fragt. Die nächste Anmeldung bekommt ein Token ohne die Rolle, und dieses Token verwendet der Terminal-Clip weiter oben.
